Task Execution Planner

Dokumentacja projektowa i użytkowa · 11 listopada 2026 · autor: Voytas

1. Podsumowanie zmian 0.2.0

Wersja 0.2.0 jest rewizją 0.1.0 po trzech testach zachowania. Zmiany dotyczą procesu planowania, nie domen testowych.

TestUjawniona słabośćUogólniona poprawka

Zakres pozostaje ogólny. Przykłady rynku, pogody czy subskrypcji nie są regułami domenowymi skilla. Są jedynie przypadkami testowymi dla uniwersalnych zasad planowania.

2. Cel i granice

Cel: dla pojedynczego zadania zaproponować minimalny plan, który wskazuje co zrobić, czym, na jakich danych, w jakiej kolejności, jak sprawdzić poprawność i gdzie potrzebna jest decyzja lub zgoda człowieka.

  • Skill tworzy plan, nie wykonuje go.
  • Nie jest runtime, schedulerem, agentem autonomicznym ani menedżerem połączeń.
  • Plan nie jest zgodą na działanie.
  • Jeśli użytkownik osobno zleca wykonanie, wykonawca musi korzystać z rzeczywiście dostępnych i autoryzowanych zdolności oraz raportować dowody wykonania.

3. Metody wykonania

MetodaRolaPrzykłady
LLMRozumienie i ocena.Interpretacja, synteza, priorytety, rekomendacja jakościowa.
APPJawne, powtarzalne reguły.Obliczenia, walidacja, parsowanie, transformacja, agregacja, testy.
TOOLZewnętrzne dane lub istniejąca zdolność.Wyszukiwarka, API, repozytorium, pliki, baza, konektor.
HYBRIDMetody praktycznie nierozdzielne.Rzadki przypadek, gdy nie da się wyodrębnić osobnych wyników etapów.

Domyślnie rozdziel pobieranie, walidację, obliczenia, interpretację i decyzję. APP nie oznacza automatycznie budowy aplikacji: może oznaczać mały skrypt lub istniejące środowisko. Wdrożenie kodu musi być uzasadnione precyzją, skalą, powtarzalnością, audytowalnością lub integracją.

4. Proces planowania

  1. Ustal wynik, zakres i wykluczenia.
  2. Oceń złożoność: DIRECT, SEQUENTIAL, PARALLEL, MIXED.
  3. Podziel na zadania z osobnymi wynikami.
  4. Wybierz metodę dla każdego zadania.
  5. Sprawdź dostępność narzędzi, danych, runtime i uprawnień.
  6. Zdefiniuj pochodzenie danych i bramki kompletności.
  7. Określ algorytmy, jednostki i przypadki brzegowe dla APP.
  8. Ułóż zależności, bramki ludzkie i bezpieczeństwa.
  9. Określ awarie, fallbacki, kryteria stop i walidację końcową.
  10. Przedstaw zwięzły plan z wyraźnym statusem PLANNED.

Nie wypełniaj wszystkich pól mechanicznie. Pomijaj elementy nieistotne dla danego zadania.

5. Scope Gate

Przed wyszukiwaniem lub implementacją zapisz kryteria, które determinują poprawny wynik:

  • co wchodzi i nie wchodzi w zakres;
  • jak definiowane są porównywane kategorie i terminy;
  • jakie podmioty, lokalizacje, okresy, interwały, jednostki i poziom szczegółowości są wymagane;
  • jakie ograniczenia budżetu, dostępu, czasu i formatu obowiązują;
  • jakie warunki oznaczają wynik wystarczający.

Jeżeli brak definicji zmienia rezultat, zadaj jedno konkretne pytanie. W przeciwnym razie jawnie przyjmij rozsądne założenie.

6. Data Provenance Gate

W przypadku istotnych danych zewnętrznych plan ma określić źródło, czas pobrania, zakres, parametry, jednostki, znaczenie pól i transformacje. Preferuj źródła pierwotne. Dla faktów zmiennych w czasie nie polegaj na pamięci modelu.

StatusZnaczenie
PRIMARY_VERIFIEDSprawdzone bezpośrednio w źródle pierwotnym.
SECONDARY_VERIFIEDSprawdzone w źródle wtórnym; nie jest równoważne źródłu pierwotnemu.
PARTIALNiepełny zakres lub brakujące pola.
CONFLICTINGŹródła istotnie się różnią.
UNVERIFIEDBrak niezależnej weryfikacji.

Zakaz cichej substytucji: nie zastępuj wskazanego API, instrumentu, okresu, populacji ani miary danymi proxy bez oznaczenia różnicy. Fallback powinien ujawnić utratę porównywalności; jeśli zmienia znaczenie zadania, wymaga zgody użytkownika.

7. Input Completeness Gate

Przed obliczeniami i wnioskami sprawdź właściwe dla zadania warunki:

  • obecność pól, typy i oczekiwaną liczbę rekordów;
  • pokrycie czasu/encji, kolejność, duplikaty i luki;
  • świeżość, tożsamość źródła, jednostki i semantykę;
  • wartości null, błędne, skrajne i zakresy plausibility;
  • zgodność danych surowych z agregatami i transformacjami.
StatusDziałanie
PASSMożna wykonać zależne zadania.
PARTIALDozwolony tylko jawnie ograniczony wynik częściowy.
BLOCKEDZatrzymaj obliczenie/wniosek; wskaż brak i sposób odblokowania.

Nie wolno podawać definitywnego wyniku, gdy wymagane wejścia są zablokowane. Sam fakt, że API zwróciło HTTP 200, nie potwierdza kompletności semantycznej danych.

8. Deterministic Boundary

Dla zadań APP określ algorytm, formuły, jednostki, precyzję, zaokrąglenie, normalizację, obsługę braków i wartości brzegowych. Zaplanuj test znanego wyniku lub inwariant. Zachowaj surowe wejścia lub odtwarzalny identyfikator danych.

Dobierz model matematyczny do semantyki danych: średnia arytmetyczna nie jest uniwersalna (np. dane kołowe, ważone lub porządkowe wymagają właściwej metody). Kod wylicza; LLM interpretuje i wyjaśnia. Nie przypisuj LLM odpowiedzialności za formalną poprawność obliczenia.

9. Human Decision / Approval Gates

TypZnaczenieWymagane zachowanie
HUMAN_DECISIONUżytkownik wybiera preferencję, wariant lub kierunek.Przedstaw porównywalne opcje, kryteria i kompromisy; zatrzymaj się do wyboru.
HUMAN_APPROVALUżytkownik zatwierdza działanie o skutkach.Opisz zakres, skutki i odwracalność; nie wykonuj bez wystarczającej zgody.

Wybór wariantu do dalszej analizy nie jest automatycznie zgodą na wykonanie działania zewnętrznego. Bramka decyzji i bramka autoryzacji to dwa odrębne mechanizmy.

10. Failure Handling & Adaptive Replanning

Dla materialnych awarii określ sygnał wykrycia, wpływ na zależności, bezpieczeństwo ponowienia, minimalny fallback i warunek zatrzymania. Po niepowodzeniu zmieniaj tylko dotknięte kroki, zachowując poprawne wyniki. Ujawniaj zmianę źródła, założeń lub zakresu.

  • SAFE — retry nie powoduje dodatkowych skutków.
  • CONDITIONAL — retry po sprawdzeniu stanu lub warunku.
  • UNSAFE — nie ponawiaj automatycznie.
  • NOT_APPLICABLE — retry nie dotyczy.

11. Stopping Criteria

Ustal, kiedy dalsze poszukiwanie lub przetwarzanie przestaje wnosić wartość. Przykładowe warunki: pełne pokrycie wymaganych rekordów, sprawdzenie źródeł pierwotnych, osiągnięcie limitu czasu/kosztu, brak istotnej niepewności albo jawne zaakceptowanie pozostałych ograniczeń.

Nie twierdź, że research jest wyczerpujący, jeśli nie sprawdzono całego zdefiniowanego zakresu. W raporcie podaj, co sprawdzono i czego nie sprawdzono.

12. Kontrakt planu

Markdown jest domyślny. YAML stosuj tylko, gdy potrzebny jest handoff maszynowy. Referencyjna struktura znajduje się w references/plan-schema.yaml. Pola obejmują: goal, scope, tasks, method, input/output, dependencies, capability availability, provenance, input gate, processing contract, validation, human gate, failure handling, stopping criteria, deliverables i status.

Każdy plan ma status PLANNED. Plan musi odróżniać propozycję od wykonania i zawierać kryterium zakończenia całego celu. Nie wypełniaj pól nieistotnych placeholderami.

13.1 Kryteria wydania

  • Poprawny frontmatter z name i description.
  • Nazwa katalogu zgodna z name.
  • Brak domenowych ograniczeń w core skill.
  • Scope, provenance, completeness, deterministic, human, failure i stopping gates są spójne w całym pakiecie.
  • Brak twierdzeń o wykonaniu bez dowodów.
  • Instrukcje pozostają proporcjonalne i nie wymuszają zbędnego APP/HYBRID.

Wersja pozostaje eksperymentalna. Trzy testy uzasadniają rozszerzenie reguł, ale nie dowodzą jeszcze skuteczności w każdej domenie. Kolejny etap to testy regresyjne na różnych klasach zadań, a nie dodawanie kolejnych domenowych wyjątków.
